What each hypothesis showed:
- **Zone 0.2/0.8 is a fair negative result.** The narrower zone doubles trades at 500k/5M (60 → 115) and costs about 1.1 pp. The whipsaw-reduction idea was wrong: a narrower zone maps the composite onto a steeper allocation slope, so it amplifies moves.
- **The stretched-band gate is a fair negative result, and the mechanism ran opposite to intent.**
  - The gate returned `None` (hold the previous target) on 55.4% of bars, yet trades *rose* from 60 to 70 and fees rose 22%.
  - Every target it let through came from a stretched bar, so each one was extreme. Holding it while price reverted kept the drift deltas large. This is the same accumulate-then-cross shape as `signal_block_secs` at 50k (doc, "Evaluation capital").
- **Threshold 0.15 is the best diagnostic result on record.**
  - Against equal-weight at 0.10, at 500k: fees −57% (3,941 → 1,683 JPY), return +0.47 pp, Sharpe +0.74.
  - Against the dev baseline at 500k: return −16.34% → −3.22%, Sharpe −28.18 → −5.39.
  - It still trails the static mix by 0.59 pp at 500k and 0.52 pp at 5M.
  - It is scored on fees, not trade count, per the doc. At 50k it is lot-floor-inert: economically identical to the 0.10 reference, with only `orders_below_min` differing (51 vs 335).

## Enabling changes

Suspected defects, not fixed:
- **The dashboard shows a false neutral when `compute_btc_target` returns `None`.** `handle_indicator` broadcasts `agg_normalized = combined.unwrap_or(0.5)`, so the dashboard shows 0.5 while an extreme sticky target is held. This only matters if a gating variant like today's is ever adopted, so it was not fixed.
- **Live and backtest evaluate the signal at different cadences.** Live re-evaluates on the forming bar about every 250 ms; the backtest evaluates once per closed 60s bar. This difference already exists. Any threshold- or gate-style rule would flip more often live than the backtest shows. It has not been measured.
- **Copying `run.db` while its WAL file exists can miss rows.** The worktree agents checked: the WAL held no extra rows this run, and all runs saw the same 15,587 window candles. Future agent prompts should say to checkpoint or copy `-wal` too.
- Still open from earlier runs:
  - The live `SignalEngine` cannot supply `realized_vol`.
  - The live `fee_pct()` is hardcoded at 0.0015 (touches live trading).
  - `Simulator::run` discards `send_order` errors.

## New hypotheses generated this run

- **equal-weight-rebalance-10m-zone-020-080** (algorithm): 2026-10-28 lead #2, which asked for zone parameters on top of equal weights. The idea was that equal weights change the composite's dispersion, so the code-default zone 0.2/0.8 might cut edge whipsaw.
- **stretched-band-gated-equal-weight-10m** (algorithm): literature-motivated (De Nicola 2021: stronger reversals after larger moves, at 1-4h horizons). It is also a cost-side hypothesis: it only re-targets when %B ≤ 0.2 or ≥ 0.8, and it uses only fields the live engine already supplies.
  - Pros: same asset, similar horizon.
  - Cons: 2015-18 sample, in-sample, no fees.
- **equal-weight-rebalance-10m-threshold-015** (algorithm): the cost-side hypothesis required by the warning rule (21 consecutive negative runs at 500k). It raises `allocation_threshold` 0.10 → 0.15 on equal weights + 600s. The 50k inertness was stated in advance.
