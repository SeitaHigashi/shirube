### The two 1-trade results are not a measurement — they are the lot floor

`hourly-spacing-zone-damping-090-combined` and `zone-damping-085` both collapse to **exactly one
trade** at the primary capital, and their reports are near-identical to each other despite
expressing different mechanisms (one stacks hourly spacing on ×0.90 damping; the other is ×0.85
damping alone). Both report `sharpe_minus_static_mix: +0.0011` and
`excess_return_vs_static_mix_pct: +0.0117`.

**That positive number is arithmetic, not alpha, and must not be read as the strategy finally
beating its benchmark.** A run that makes one buy and holds *is* a static mix at its own average
exposure; the benchmark is rebuilt at each run's own `avg_btc_exposure`, so it converges on the
run itself and the difference goes to zero from whichever side rounding puts it. The same artifact
was recorded on 2026-09-16 (`≈ +0.00075` at 50k) and is called out in the doc. Two independent
hypotheses reproducing it to four decimal places is confirmation of the artifact, not evidence of
an edge.

The substantive finding underneath it is that **the ×0.85 damping dose is not a mild extension of
×0.90 — at the primary capital it falls off a cliff.** On 2026-09-18's window ×0.90 produced 44
trades (67% of that baseline, promoted as PR #27). Today ×0.85 produces **1**. That is not a
dose-response curve; it is a threshold effect, and the mechanism is visible in the 500,000 JPY
column, where ×0.85 keeps **623 trades (78% of the 803 baseline)** and would comfortably clear the
trade-count floor. The damping barely throttles the strategy at all in economic terms — it shrinks
each allocation delta by 15%, which at 500,000 JPY merely makes orders smaller, but at 50,000 JPY
pushes nearly all of them under the 0.001 BTC floor where they vanish entirely. The 2026-09-18
finding that the primary capital is "chaotic for this family" is now much better explained: it is
not chaos, it is a discretiser, and any band-width hypothesis is really measuring how a continuous
knob interacts with a hard floor.

This also means **the promoted ×0.90 config (PR #27) sits very close to that cliff** on the
capital the operator actually trades. A human merging it should know that the neighbouring dose in
the same direction produces a one-trade portfolio.

### The result that matters most this run is about a merged and an open PR, not about today's candidates

`rebalance_interval_secs: 3600` — promoted on 2026-09-18 and **currently open as PR #28** — scores
**30 trades against today's baseline of 88, a ratio of 34%**. That is below `MIN_TRADE_COUNT_RATIO`
(50%). **Re-run against today's holdout, the configuration this pipeline promoted two days ago
would be rejected**, on the same criterion that rejected all three of today's candidates.

Nothing about that is a defect in the promotion rule or in PR #28's original measurement — both
were correct on their own windows. It is a statement about **stability**: the trade-count criterion
is the binding constraint on every recent verdict, and it is evidently not stable across a two-day
shift in a 14-day window. That makes it the single most important thing for a human to know before
merging PR #27 or #28, and it is the strongest argument yet that this pipeline's promotions need
either a wider evaluation window or a multi-window re-check before they are treated as decisions.
The DB now spans **42 days** (2026-08-09 .. 2026-09-20), comfortably past bitFlyer's 31-day
retention wall, so a wider holdout is for the first time actually available.

## Leads for the next run

1. **Widen the holdout window.** This is now the highest-value change available and it is finally
   possible: the accumulated DB spans 42 days, past the 31-day wall. Today's run established that
   the trade-count criterion — the binding constraint on essentially every recent verdict — flips
   on a two-day window shift (PR #28's config: promoted at 67% of baseline on 2026-09-18, 34% of
   baseline today). A 14-day holdout is not producing stable decisions, and every other lead is
   worth less until the measurement is trustworthy. Changing the holdout width is a doc change plus
   a routine-prompt change, not a code change.
2. **Re-check the two open PRs (#27, #28) on the current window before merging.** Both were
   promoted on 2026-09-18 and neither reproduces today: #28's config now fails the trade-count
   floor outright, and #27's neighbouring dose (×0.85) collapses to one trade at the operator's
   capital. This is a human decision, not something the pipeline should act on unilaterally, but it
   should be made with today's numbers in hand.
3. **The lot-size floor, not any config field, is what the primary capital measures.** With
   `orders_below_min: 6182` against 88 executed trades, ~98.6% of intended actions are discarded at
   50,000 JPY. Any hypothesis whose mechanism is "make each allocation delta smaller" — the whole
   zone-damping family — is really a hypothesis about that floor, and its 50,000 JPY result is a
   threshold effect rather than a dose-response. Worth considering whether the pipeline should
   report an explicit "fraction of intended deltas executed" diagnostic so this is visible on every
   run instead of being rediscovered.
4. **Blocking edges out spacing, on one window.** `signal_block_secs: 3600` beat
   `rebalance_interval_secs: 3600` on fees (−6.1%), return and Sharpe at 500,000 JPY today. Since
   the former is already merged, the cheapest next question is whether #28 adds anything on top of
   it — a combined-throttle configuration measured against blocking alone, rather than against the
   unthrottled baseline.
5. **There is still no measured gross alpha.** Six consecutive runs below the exposure-matched
   static mix, today by the largest margin ever recorded, and against a market that was essentially
   flat (+1.43% buy-and-hold) — so this window's deficit cannot be attributed to direction. Every
   promoted change to date moves the result *toward* the static mix from below without crossing it.
   The honest standing description of this system is unchanged.
6. **`sentiment_weight` remains untestable by construction** in this harness (2026-09-10); lead #4
   from 2026-09-14 (de-duplicating sub-signal votes) stays closed (2026-09-15).

## Operational notes from this run

- **The 2026-09-19 run died mid-cycle**, after committing its generated hypotheses but before
  writing a report or updating `tried.json`. The failure mode was benign — the pipeline is
  idempotent enough that today simply picked up the three orphaned candidates via their
  `content_hash` — but it means the consecutive-negative-run counter has a one-day hole in it, and
  no baseline was recorded for 2026-09-19. Committing generated hypotheses in their own commit
  *before* running them, which that run did, is what made the recovery clean; it is worth keeping.
- **The coordinator computed every variant report and every `compare-backtest` itself**, in the
  main checkout, rather than relying on an agent's reading — continuing the practice adopted
  2026-09-18. The three worktree agents ran the same three configs independently as a cross-check.
- **All three candidates were parameter hypotheses**, so no worktree produced a code diff and
  nothing needed cleaning up beyond the worktrees themselves. That is the fourth consecutive run in
  which every hypothesis was expressible as pure configuration.
- **`tried.json` records gained a `sharpe_absolute_delta` field** this run. The documented schema's
  `sharpe_improvement_pct` is `null` by construction whenever the baseline Sharpe is non-positive,
  which it has been on every run since 2026-09-14 — so the registry had stopped recording *how much*
  anything improved. The new field is additive; nothing reads the old one positionally.
