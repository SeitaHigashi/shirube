  was deliberately not attempted here.

  This variant is also the clearest possible demonstration of why the
  trade-count floor exists: a strategy that never trades is scored as
  "Sharpe improved by 10.566, drawdown improved by 7.33pp". Both statements
  are arithmetically true and completely meaningless.

## The trade-count floor is now the binding constraint

Three for three rejections on one criterion, in a run where the diagnosis
being tested *is* excessive turnover, is a structural result rather than
three unlucky variants.

`MIN_TRADE_COUNT_RATIO = 0.5` in `src/backtest/report.rs` is a **relative**
test — candidate trades ≥ 50% of baseline's — but its stated rationale is an
**absolute** one: *"too few trades makes the comparison statistically
unreliable."* Those come apart badly when the baseline itself is at 91.8
trades/day:

- 204 trades over 14 days (14.6/day) is not a statistically unreliable
  sample by any ordinary standard. It is rejected for being 16% of an
  outlier baseline.
- Any variant that meaningfully reduces turnover from a 10×-too-high
  baseline mechanically fails a 50%-relative floor. **The hypothesis class
  the doc itself nominates as "the most obvious hypothesis source available
  right now" is currently unpromotable by construction.**
- Yet the floor is doing real work in the same run: it is the only thing
  that rejected the 0-trade variant.

Both failure modes appear in this one run, which makes the shape of the fix
fairly clear: keep a floor, but make it *relative **or** absolute,
whichever is more permissive* — e.g. promote when
`trade_count_ratio ≥ 0.5 || candidate.total_trades ≥ 50`. That still
rejects 0 trades and the 1-trade regression of `fbce478`, while letting a
204-trade or 609-trade candidate be judged on its Sharpe and drawdown.

**I have not made this change.** The promotion rule is the pipeline's
integrity mechanism, the doc says explicitly that it "is not re-derived by
the agent, only invoked", and it is a policy parameter a human fixed
deliberately in the "Fixed parameters" table. Proposing an amendment in the
same run in which three of my own variants failed it is exactly the kind of
judgement that should not be made unilaterally, however good the argument
looks from here. It needs a human decision; the evidence is above.

Note also that a lower floor would very likely have changed today's outcome:
`higher-allocation-threshold` and `trend-weight-half` both clear every other
criterion.

## Enabling changes

Two fixes, each on its own branch and its own PR, per the doc's rules.

**1. `scripts/backtest-data.sh` could not run in the cloud routine** (PR
#13). It shelled out to `gh` and `sqlite3`; the container has neither. Both
now have fallbacks the image does have. Verified for real: this run's DB
restore (33,452 bars, `BACKFILL_DAYS=2`) went through the new `curl` +
python3 path.

**2. Slippage was a price shift, not a cost** (PR #14). `Simulator::run` set
`best_bid`, `best_ask` **and** the mark-to-market price all to
`close * (1 + slippage_pct)`, and `MockExchangeClient::send_order` filled
both sides at `ltp`. A buy-then-sell round trip at an unchanged price
returned exactly what it paid. The backtest charged **nothing whatsoever
for turnover** beyond the mock's tiered exchange fee — while this pipeline
spent five runs reasoning about fee and slippage drag. The old
`apply_slippage` doc comment even stated the intent correctly ("buys cost
more and sells receive less"); the code did the opposite for sells.

Symptom, on this run's baseline, unfixed code, all else equal:

| `--slippage-pct` | return | Sharpe |
|---|---|---|
| 0.0 | −6.661% | **−11.183** |
| 0.02 | −7.842% | **−3.281** |

A 2% round-trip cost made risk-adjusted performance 3.4× *better*. After the
fix, cost is monotonic: −6.661% / −11.183 at 0.0, −21.050% / −38.543 at
0.001, −53.816% / −95.566 at 0.01.

**Effect on past results, as the doc requires.** Every report in this
directory up to and including Run 1 of today was measured with turnover
effectively free at the default `--slippage-pct 0.001`. This run's baseline,
same window, same config, same data:

| | as measured (this run) | corrected |
|---|---|---|
| `total_return_pct` | −6.72 | **−21.05** |
| `sharpe_ratio` | −10.57 | **−38.54** |
| `max_drawdown_pct` | 7.33 | **21.03** |
| `win_rate` | 0.732 | 0.079 |

The true cost of 91.8 trades/day was understated by roughly **14 percentage
points of return over 14 days**. Comparisons *within* any past run remain
internally valid — baseline and candidate shared the distortion — but the
distortion was **not neutral across hypotheses**: it systematically
flattered high-turnover variants and understated every turnover-reducing
one. That is the exact hypothesis class this run and the doc's own guidance
are working on, so past rejections in that class should be read with
suspicion. Concretely, `higher-allocation-threshold` measures **+3.21**
Sharpe against the unfixed baseline and **+21.71** against the corrected
one.

Today's cycle was deliberately scored on **unfixed** `dev` so its baseline
and all three variants stayed comparable to each other. Tomorrow's run
inherits the fix if PR #14 merges, and its baseline will move accordingly —
do not compare across that boundary.

Found and deliberately **not** fixed:

- **`push` to the `backtest-data` release is blocked by the environment, so
  DB accumulation has stalled.** The routine's outbound HTTPS goes through a
  relay that injects its own GitHub credentials and accepts only JSON
  bodies: asset deletion returns 403, asset upload returns 415
  (`Request bodies must declare Content-Type: application/json`). No
  scripting gets around that — a binary upload is not a JSON body. `pull`
  works, so this run restored and backtested normally, and it topped
  `run.db` up to **33,951 bars** (`2026-08-09T04:03Z` → `2026-09-09T19:12Z`,
  +499 bars, oldest bar unchanged, zero duplicate timestamps) — and could
  not publish it. Nothing is lost yet, because the stored copy still spans
  roughly the full 31-day retention window, but **from here each day's
  increment is dropped and the lookback stops growing**. Needs a human
  decision: run `scripts/backtest-data.sh push --db ./run.db` by hand, or
  move backfill-and-push into a GitHub Actions workflow (which must live on
  `main` to be dispatchable, so it needs a `dev` → `main` release first).
  Documented in PR #13 and in `docs/self-improvement-loop.md` on that
  branch.
- **The relay also blocks branch deletion**, by `git push --delete` and by
  the API alike (403, *"Write access to this GitHub API path is not
  permitted through this proxy"*). The `cost-aware-rebalance-filter` agent
  pushed its worktree branch before reporting, so
  **`worktree-agent-a626114efaa265bd1` is still on `origin`** and needs
  `git push origin --delete worktree-agent-a626114efaa265bd1` from a human
  shell. Its worktree and local branch were removed normally. Two
  preventions for future runs: tell worktree agents explicitly not to push,
  and expect remote cleanup to need a human.
- **`Simulator::run` still hardcodes an empty news slice**
  (`src/backtest/simulator.rs`), pinning `sentiment_normalized` at 0.5 so no
  variant can exercise the sentiment channel. Fourth consecutive run on the
  record. It also directly caps `cost-aware-rebalance-filter`'s conviction
  proxy at 0.35, which is part of why that gate was unsatisfiable.
- **The tried-hypothesis registry has no notion of *which baseline* a
  verdict was measured against.** All 17 prior entries were measured on
  CoinGecko 1h data with the broken cost model; several are now known to be
  arithmetic rather than evidence (the doc already says this of
  `add-volume-weighted-ma-indicator`). Because dedup is by `content_hash`
  over `trading_config` + `kind` + `code_change_summary`, none of them can
  ever be re-tested on the corrected pipeline — including `wide-zone-band`,
  which is sitting in an open PR on exactly those superseded numbers. A
  `baseline`/`data_source` field in the schema, with dedup keyed on
  (content_hash, baseline), would fix this. Not implemented: it changes the
  loop's core bookkeeping semantics and belongs with the promotion-rule
  decision above.

## New hypotheses generated this run

`CANDIDATES` was empty — all 17 pre-existing `experiments/hypotheses/*.json`
files hash-matched entries in `experiments/tried.json` (pure hash matching
via `shirube hypothesis-hash`, no name fallback). Three were generated per
the doc's Step 3 and all three were tried the same run, so none carry over.

- **higher-allocation-threshold** (parameter): grounded in this run's own
  baseline — 91.8 trades/day with a 73.2% win rate and a −6.72% return, the
  textbook cost-dominated shape, and the doc's explicit nomination of an
  `allocation_threshold` hypothesis as "the natural first thing to test".
  Only the opposite direction had ever been tried (`lower-allocation-threshold`,
  rejected 2026-09-08).
- **cost-aware-rebalance-filter** (algorithm, literature-motivated —
  arXiv:2606.00060): the same turnover deficit, attacked with a
  conviction-versus-cost gate rather than a fixed threshold. See the
  Pros/Cons in "Literature reviewed" and the null result above.
- **trend-weight-half** (algorithm): Run 1's lead #3 — nothing said 0.25 was
  right, it was only the mirror of a rejected variant — plus a second
  reason: the −0.028 hourly autocorrelation that justified it re-measures to
  **−0.0146 at 1-minute resolution** on real bitFlyer bars over the
  pre-holdout window, half the magnitude at the resolution the engine
  actually trades.

**Leads for the next generation cycle**, in rough order of promise:

1. **The promotion rule's trade-count floor** (see its section above). This
   is the highest-value item and it is a human decision, not a hypothesis.
   Until it is settled, the turnover hypothesis class cannot produce a
   promotion no matter how good a variant is.
2. **Re-baseline everything once PR #14 merges.** The corrected cost model
   moves the baseline from −6.72% to −21.05% and changes which hypotheses
   look good. `higher-allocation-threshold` goes from +3.21 to **+21.71**
   Sharpe under it.
3. **A holding-horizon cost gate.** `cost-aware-rebalance-filter` failed
   because a 6.5bp per-bar expected move cannot repay a 25bp round trip at
   1-minute resolution. Comparing expected move against cost over N bars of
   expected holding time is a genuinely different rule and the honest way to
   test the mechanism.
4. **Walk the rest of the family-weight curve.** 0.5 beat 0.25 on every
   axis except trade count; 0.75 is the untested point between it and the
   rejected 1.0.
5. **`rebalance_interval_secs` is untestable as a hypothesis** — worth
   recording so nobody proposes it. `Simulator::run` evaluates every candle
   and never reads the field; only the live engine's periodic ticker uses
   it. A hypothesis varying it would measure exactly nothing, like
   `sma-regime-gate` did.
