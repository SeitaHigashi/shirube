All three `sharpe_improvement_pct` values above are `compare-backtest`'s
absolute Sharpe delta, not a percentage — the baseline Sharpe is
non-positive (-41.43), so the tool reports `sharpe_improvement_pct: null`
and falls back to the absolute-delta threshold (>= 0.1) instead. The
same absolute-delta numbers are what's stored in each `tried.json` entry's
`sharpe_improvement_pct` field for this run, since the schema doesn't
have a separate field for the non-percentage case.

Verdict detail per `shirube compare-backtest`:
- **shorter-hourly-indicator-periods**: Sharpe improved by 14.81 (a real,
  large improvement) and trade count is healthy at 151% of baseline, but
  it was rejected purely on the "max drawdown must not worsen" rule —
  drawdown ticked up by 0.0020 percentage points (4.2896% → 4.2915%),
  which is almost certainly simulation noise rather than a meaningful
  regression, but the promotion rule (correctly, per its own design) does
  not carve out an epsilon for "worsened by a hair."
- **lower-allocation-threshold**: rejected outright — Sharpe got *worse*
  (-1.96 absolute) and drawdown worsened by 0.30pp. Isolating
  `allocation_threshold` alone (0.15 → 0.05) with default indicator
  periods let more low-conviction rebalances through, which hurt more
  than it helped once the underlying signal was directional and noisy
  most of the time.
- **continuous-crossover-subsignals**: touches
  `TradingEngine::compute_btc_target`'s body (confirmed, not its
  signature) per the 2026-09-08 policy allowing this on a dedicated
  worktree branch. `cargo test` passed 186/186 including the updated
  `compute_btc_target_*` expected values. Sharpe improved by 16.54 (the
  best of the three) and drawdown *improved* by 1.33pp — but trade count
  collapsed to 27% of baseline (10 vs 37), well under the 50% floor, so
  it was rejected on sample-size grounds despite otherwise looking like
  the strongest candidate. Its worktree and branch
  (`worktree-agent-a87b70de0e8f02f46`) were deleted after the rejection
  per the pipeline's cleanup step — nothing to PR.

Verdict detail per `shirube compare-backtest`:
- **medium-hourly-indicator-periods**: a deliberately less aggressive
  step than Run 1's near-miss `shorter-hourly-indicator-periods` (SMA
  72/EMA 36/RSI 21/MACD 17-35-12/Bollinger 30 instead of 48/24/14/26/20),
  intended to test whether a smaller period reduction would avoid the
  0.002pp drawdown uptick that sank the more aggressive variant. Instead
  it produced a *larger* drawdown regression (+0.25pp, not noise-level
  this time) for a smaller Sharpe gain than the fully-shortened variant
  — the near-miss in Run 1 does not appear to generalize to "any
  shortening helps"; the relationship between period length and
  drawdown looks non-monotonic here rather than a simple dial. Trade
  count (37) came out almost identical to baseline (36), well within
  the 50% floor either way.
- **damped-crossover-subsignals**: narrowed Run 1's rejected
  `continuous-crossover-subsignals` saturation band from 2% to 0.5%
  relative distance, specifically to recover trade count (Run 1's
  version collapsed to 27% of baseline). It worked partially — trade
  count recovered from 27% to 47% of baseline, and both Sharpe (+10.06)
  and drawdown (-0.90pp, improved) are strong — but 47% still falls
  just short of the 50% floor, so this is rejected on the same
  sample-size ground as its Run 1 predecessor, despite being a
  meaningfully better result. This is the closest-to-promotable variant
  across both of today's runs.
- **volatility-scaled-zone-width**: the literature-motivated hypothesis
  (see above). Widening/narrowing the zone dead-band by Bollinger
  bandwidth performed worse than baseline on every axis — Sharpe
  dropped further (-5.19 absolute) and drawdown worsened by 0.49pp, the
  largest drawdown regression of any hypothesis tried so far in either
  run. `cargo test` passed 190/190 (4 new tests for the added
  `volatility_adjusted_zone` function), and `compute_btc_target` was
  confirmed byte-for-byte untouched (only `apply_zone`'s call sites in
  `handle_indicator` and `Simulator::run` changed). One plausible
  explanation: shirube's 14-day BTC/JPY holdout may not have had large
  enough bandwidth swings for the paper's underlying "volatility regime"
  concept to bind usefully, or the specific heuristic constants chosen
  ([1,10]% bandwidth range, 0.7-1.3 widening factor — explicitly flagged
  in the hypothesis's own `paper_reference.cons` as untested guesses
  translating the paper's concept, not values from the paper itself)
  were simply a poor fit. Per the doc's design, the paper's own reported
  Sharpe never substituted for this backtest gate, which is exactly what
  caught this.

### Operational notes from this run

- **Worktree/origin race condition**: the 3 new hypothesis files were
  written locally and only committed+pushed to `origin/dev` *after* the
  3 `isolation: "worktree"` agents had already been launched and had
  run their step-0 `git fetch && git rebase origin/dev`. All 3 agents
  initially reported the hypothesis file missing from their worktree.
  This was caught by checking each worktree's `git log` directly rather
  than trusting agent self-reports, and fixed by pushing immediately and
  asking each agent to re-fetch/rebase. **Action for future runs**: push
  any newly-generated `experiments/hypotheses/*.json` files to
  `origin/dev` *before* launching the worktree agents that need to read
  them, not after — launching and pushing were done in the wrong order
  this run.
- **Agents reporting false completion**: two of the three worktree
  agents (the parameter-only one and one algorithm one) reported task
  completion multiple times via the task-notification channel while
  their actual message content was a passive "standing by for the
  build/notification to complete" rather than a finished result. Each
  had to be resumed via a direct status-check message before it
  produced real output. This cost significant wall-clock time this run
  (all three worktree agents took 3-13 minutes each, largely full
  from-scratch release builds with no shared incremental cache between
  worktrees). Worth investigating whether these agents' use of a
  Monitor-style wait pattern is reliably resuming on its own or needs a
  more explicit instruction not to end a turn while a background
  process it's waiting on is still running.
- **Same-day double run**: this is the second scheduled/automated
  firing of this pipeline on 2026-09-08 (Run 1 completed 00:13 UTC,
  this run started ~11:53 UTC). It is unclear from this session whether
  a twice-daily cadence is intentional or this was a duplicate firing of
  what should be a once-daily schedule; flagging for whoever owns the
  cron configuration to check, since the "Cadence: daily" line in
  `docs/self-improvement-loop.md`'s parameters table suggests once/day
  was the intent.
