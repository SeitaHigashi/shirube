- **code-default-allocation-threshold** (0.10 → 0.15) — **rejected on the
  trade-count floor and nothing else**, at 46% of baseline trades (598 vs
  1288), 3.6 percentage points under the 50% requirement. Both other criteria
  passed: return −8.33% → −7.74%, Sharpe −13.540 → −12.767, max drawdown
  8.83% → 8.35%. Turnover fell 92.0 → 42.7 trades/day; win rate 72.0% → 66.8%,
  the same fewer-larger-round-trips shape Run 2 saw at 0.25. No code change.
  **What makes this one different from an ordinary near miss is where the
  value came from:** `TradingConfig::default()` has shipped
  `allocation_threshold: 0.15` since commit `7245310` ("perf: raise
  allocation_threshold from 0.05 to 0.15", a hand-made change), while
  `experiments/baseline-config.json` has always held `0.1`. See "The baseline
  config has never matched the shipped default" below.
- **rolling-vol-scaled-exposure** — rejected on Sharpe and drawdown, clearing
  the trade-count floor comfortably at 125%. `cargo test` **216 passed / 0
  failed** (up from 205 on `dev`, +11 new tests); no existing test weakened,
  deleted, or re-expected — every pre-existing `IndicatorPoint` literal sets
  the two new fields to `None`, which the guard maps to `k = 1.0`, so those
  points are unaffected by construction. `compute_btc_target`'s signature
  verified byte-for-byte unchanged; its **body was modified**. Diff confined
  to `src/signal/mod.rs`, `src/signal/engine.rs`, `src/trading/engine.rs`.

  **This variant's instrumentation overturns last run's diagnosis, which is
  worth more than the verdict.** `realized-vol-scaled-exposure` was rejected
  on 2026-09-09 with the conclusion that a *fitted* reference constant
  (`REFERENCE_HOURLY_VOL = 0.0042`) had failed to transfer, putting mean
  `k` at 1.312 and pinning it at the amplification cap for 61% of the window —
  so the rule amplified exposure instead of damping it. Today's version removes
  every fitted constant, estimating the reference as a short/long realised-vol
  ratio from the same data. It reproduced the failure almost exactly:

  | metric | value |
  |---|---|
  | mean `k` | 1.1215 |
  | fraction amplifying (`k > 1`) | 60.50% |
  | fraction damping (`k < 1`) | 36.52% |
  | pinned at `VOL_SCALE_MAX = 1.5` | 35.53% |
  | pinned at `VOL_SCALE_MIN = 0.5` | 10.23% |
  | `k == 1` (long window not yet full) | 2.98% (453 candles) |

  The level shift in the fitted constant was therefore **not** the cause; it
  merely coincided with it. The real cause is a property of the estimator pair:
  at 1-minute resolution realised volatility is bursty, so the 12-hour
  standard deviation is inflated by a minority of high-volatility bars and sits
  above the typical 1-hour one most of the time. `long/short` is right-skewed
  with a median above 1, and squaring it amplifies that asymmetry, so
  `E[(long/short)²] > 1` is close to structural here — any inverse-variance
  rule built from a short/long realised-vol *standard deviation* ratio at this
  resolution will spend most of its time amplifying, whatever reference it
  uses. Unlike its predecessor this was a genuine two-sided test (36.5% of
  candles damped, 10.2% at the damping floor) and it still lost 1.90 Sharpe.
  **Two independent constructions of the same mechanism have now failed on this
  window; the "re-centre the volatility reference" lead is closed rather than
  carried forward.** If it is ever retried the fix would have to be to the
  estimator (compare medians rather than standard deviations, or drop the
  `.powi(2)`), not to the reference.

  Sanity check that the wiring was right: `k == 1` on exactly 453 candles =
  `VOL_WINDOW_LONG (720) − 267 available warmup candles`, i.e. the long window
  fills precisely where the arithmetic says it should.
- **reversion-horizon-15m** — rejected on merit, and decisively: the worst
  result this pipeline has measured on any axis. Shortening only the two
  mean-reverting indicator periods (`rsi_period` 42 → 15, `bollinger_period`
  60 → 15) tripled turnover (92.0 → 284.1 trades/day), nearly doubled the loss
  (−8.33% → −14.26%) and worsened drawdown by 5.74pp. Trend periods were left
  untouched, so this is a clean read on the reversion horizon.

  The result is the *opposite* of what arXiv:2608.21888's horizon-decay curve
  suggested and **exactly what its own cost arithmetic predicted**: the paper
  finds the gross edge peaks at ~1.3bp per trade against a 5bp round-trip cost,
  so moving to a faster horizon buys a slightly better signal and pays several
  times its value in turnover. shirube's own pre-holdout data says the same
  thing more bluntly — mean absolute move is 4.11bp at 1 bar and only reaches
  ~32bp at 60 bars, so a faster mean-reverting horizon cannot repay a
  round trip. **A paper's adopted mechanism failing on shirube's own gate is
  the design working as intended**, and it is a second independent line of
  evidence, alongside `higher-allocation-threshold` and
  `code-default-allocation-threshold`, that this strategy's deficit is
  turnover cost rather than signal horizon.

## The baseline config has never matched the shipped default

`docs/self-improvement-loop.md` defines `experiments/baseline-config.json` as
"the config the currently-running instance is assumed to use", and says to
refresh it from `GET /api/config` if the live DB-persisted config has drifted.
It holds `allocation_threshold: 0.1`. `TradingConfig::default()` in
`src/config.rs:75` holds **0.15**, and has since `7245310` — a deliberate
hand-made change ("perf: raise allocation_threshold from 0.05 to 0.15"). The
file has never carried that value; `git log -S` finds no commit that ever set
`0.1` as the code default.

Two consequences, both for a human:

1. **Every parameter verdict this pipeline has produced was measured against a
   threshold the live instance most likely does not run.** If the running
   instance's DB-persisted config came from `TradingConfig::default()`, it is
   at 0.15, and today's measurement says that config is *better* than the one
   the pipeline baselines on (+0.773 Sharpe, −0.48pp drawdown).
2. **I did not change the file.** The doc's stated source of truth is
   `GET /api/config` on the running instance, which this routine cannot reach —
   the value could equally have been edited via the UI to something else again.
   Overwriting the baseline on an assumption would silently re-scale every
   historical comparison in `experiments/reports/`. It needs an operator to
   read the live config and reconcile the two.

Note this also means `higher-allocation-threshold`'s headline +3.207 Sharpe
(2026-09-09) was measured from 0.10, not from whatever the instance runs.

## The trade-count floor, second run running

Run 2 of 2026-09-09 rejected all three of its hypotheses on
`MIN_TRADE_COUNT_RATIO = 0.5` alone, two of them after clearing Sharpe and
drawdown by wide margins, and set out the argument that the floor is
*relative* while its stated rationale ("too few trades makes the comparison
statistically unreliable") is *absolute* — which comes apart when the baseline
itself is at 92 trades/day.

Today adds one more case, and a sharper one:
`code-default-allocation-threshold` clears Sharpe and drawdown and is rejected
at **46%**, on **598 trades over 14 days**. 598 trades is not a statistically
unreliable sample by any ordinary standard; it is rejected for being 46% of an
outlier baseline. And the value being rejected is the one the source tree
ships as its default.

That is now four variants across two consecutive runs rejected on this
criterion alone, all of them turnover-reducing — the hypothesis class the doc
itself nominates as "the most obvious hypothesis source available right now".
Meanwhile the floor keeps doing real work in the same runs: it is what
rejected Run 2's 0-trade `cost-aware-rebalance-filter`, and today it is the
only criterion `rolling-vol-scaled-exposure` passed.

Run 2's proposed shape still looks right — keep a floor, but make it relative
**or** absolute, whichever is more permissive (e.g.
`trade_count_ratio >= 0.5 || candidate.total_trades >= 50`) — and would have
promoted `code-default-allocation-threshold` today.

**I have not made this change, for the same reason Run 2 did not.** The
promotion rule is the pipeline's integrity mechanism, the doc says explicitly
that it "is not re-derived by the agent, only invoked", and it is a policy
parameter a human fixed deliberately. Proposing an amendment in the second
consecutive run in which my own variants failed it does not make the argument
stronger — it makes it more suspect. The evidence is recorded; the decision is
a human's.
