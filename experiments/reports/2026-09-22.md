### `close-location-subsignal` — a clean, non-null answer to lead #3, and it is a large negative

2026-09-21's lead #3 argued that after the contrarian inversion result, the only productive direction
left was **a genuinely different signal — a new indicator or data source, not a reweighting of the
existing five sub-signals**. This is the first such test, and the first one that was only possible at
all after CoinGecko was replaced: every CoinGecko row had `open == high == low == close`, so intra-bar
range carried literally no information.

The agent's instrumentation over the exact 15,977 evaluated bars settles inert-versus-ineffective
decisively:

| metric | value |
|---|---|
| mean of the sub-signal | 0.5177 (neutral point is 0.5) |
| stdev | 0.4194 (theoretical max for a [0,1] variable is 0.5) |
| zero-range (degenerate) bars | 2,152 = **13.47%** |
| value exactly 0.0 | 4,597 = **28.77%** |
| value exactly 1.0 | 5,054 = **31.63%** |
| mean / median bar range | ¥5,041 / ¥3,259 |

**The sub-signal fired hard and often, and it is a churn generator.** 60.4% of bars sit at exactly
0.0 or exactly 1.0: at 60-second resolution on the bitFlyer tape the last tick of a bucket very often
*is* that bucket's high or low, so the close's location within its own bar is a near-binary variable
that flips almost every bar. Pushed at `TREND_SUBSIGNAL_WEIGHT` = 0.25 into a divisor that moves
2.75 → 3.00, it injects roughly ±0.058 of high-frequency noise into the composite continuously. The
consequences are exactly what that predicts: trades 31 → **83** at the primary capital, fee drag
1.20% → **2.79%**, return +5.30% → **+0.69%**, Sharpe 7.78 → **1.34**.

The mean at 0.5177 confirms it introduced no directional bias, as the hypothesis predicted by
construction — so this is not a sign error, it is a signal-to-noise failure. **Lead #3's premise is
supported and its hope is not**: an orthogonal, genuinely new observable *did* move the strategy
materially, which is more than any reweighting achieved, but it moved it decisively in the wrong
direction. A follow-up worth considering is the same observable *smoothed* over a window rather than
consumed bar-by-bar, which would keep the information and drop most of the noise.

### `relative-volume-damped-exposure` — the sign flips between capitals, and that is the finding

This hypothesis damped the composite toward 0.5 in proportion to how far a bar's volume fell below
its trailing 60-bar median, passing bars at or above the median through bit-identically. It is the
first volume hypothesis this pipeline has ever fairly tested: `add-volume-weighted-ma-indicator` was
recorded rejected at `sharpe_improvement_pct: 0.0` on 2026-09-07, but that was arithmetic, not
evidence — on CoinGecko's constant `volume: 1` a VWMA *is* an SMA.

The damping was properly exercised, not inert:

| metric | value |
|---|---|
| evaluated bars | 15,977 |
| bars with `rel_volume == None` | 0 |
| at conviction exactly 1.0 (pass-through) | **49.29%** |
| mean conviction | **0.6833** |
| below 0.5 conviction | **34.76%** |
| conviction p01 / p10 / p50 | 0.019 / 0.104 / 0.971 |

At the primary capital it did what it was designed to do: trades 31 → 19, traded volume −39%, fee
drag 1.199% → 0.754%, return +5.30% → +5.61%, Sharpe +7.78 → +8.18, benchmark deficit −2.095 → −1.696.
**At the diagnostic capitals it did the opposite, violently**: trades 835 → **1,390** at 500,000 JPY,
fees 30,710 → **39,729**, return −10.11% → **−17.79%**, Sharpe −16.38 → **−30.33**, the worst
diagnostic-capital Sharpe this pipeline has recorded. The agent's explanation is mechanical and
convincing: above the lot floor, pulling the composite toward 0.5 on a third of bars makes the target
oscillate around mid-exposure, and every wobble clears `allocation_threshold = 0.1` and becomes a
fee-paying round trip. Below the floor, the same oscillation mostly gets refused.

So this is the **third distinct mechanism** now documented whose sign depends on the evaluation
capital, after `signal_block_secs` (2026-09-21) and `zone-damping-090` (PR #27's three
non-reproducing measurements). The pattern is no longer anecdotal.

**And it would have been a no-op live even if promoted.** The agent reports that
`SignalEngine::run` builds its `IndicatorPoint` from one `Candle` at a time with no rolling volume
history, so `rel_volume` is `None` on the live path → conviction 1.0 → pass-through. It also explains
why a naive buffer there would be *wrong* rather than merely incomplete: `MarketDataBus` republishes
the same in-progress partial candle on every ticker event via `agg.peek_current()`, so appending
every received candle would fold the current bar's own partial volume into its own baseline dozens of
times per minute — the exact causality violation the hypothesis's constraints forbid. Making any
volume-conditioned mechanism live-effective needs bar-boundary-deduplicated volume history inside
`SignalEngine`, keyed on `open_time`. **That is a prerequisite enabling change, and it should be
built before another volume hypothesis is proposed** — see leads.

### `half-hour-block-hourly-spacing` — the mechanism it was built on did not reproduce

blocking with an hourly rebalance interval would cancel that inversion.

only one of the four that reduced primary-capital cost at all, and it did so by a trivial margin.

This is worth stating plainly because yesterday's report built a lead on that mechanism: **the
"blocking inverts sign at 50,000 JPY" finding is window-specific and should not be treated as
established.** The underlying floor-conversion effect is real — the baseline clears the lot floor on
31 of ~6,437 opportunities (0.48%) while `rebalance_interval_secs: 3600` clears it on 40 of ~186
(21.5%) — but which knob triggers it, and in which direction, changes between adjacent overlapping
windows. Recorded as a comment on PR #31 rather than as a new doc PR, since #31 is the open PR that
documents this class of effect.

The one durable result here is at the diagnostic capitals, where the combination is **the best
configuration this pipeline has measured at 500,000 and 5,000,000 JPY**: Sharpe +1.51 and +3.70 and a
*positive* return in both, against a baseline of −16.38/−10.11%. It is still 8.37 and 6.18 of Sharpe
below its static mix, so it does not beat holding — but it is the first config to take the diagnostic
capitals into positive territory at all.

### Suspected defects found and deliberately not fixed

- **`SignalEngine` cannot supply rolling per-bar volume history, so no volume-conditioned mechanism
  can work live.** Found by the `relative-volume-damped-exposure` agent and described above: the live
  `IndicatorPoint` construction site sees one candle at a time, and `MarketDataBus` republishes the
  same in-progress partial candle on every ticker event, so a naive buffer would fold a bar's own
  partial volume into its own baseline. Not fixed because it is a real design change to the live path,
  the hypothesis's constraints ring-fence that area, and the variant was rejected anyway. **This is the
  highest-value enabling change currently identified** — it is a prerequisite for the whole volume
  family, and the family is one of only two orthogonal information sources this strategy has left.
- **A sub-signal that is available from bar 1 defeats the warmup guard.** The `close-location-subsignal`
  diff (now deleted) placed the new arm before `if sub_signals.is_empty()`, as its hypothesis directed.
  Because `close`/`high`/`low` are `Some` from the first candle while every indicator is `None` until its
  period fills, `compute_btc_target` would return `Some` from bar 1 and the engine would establish a
  `sticky_target` from that sub-signal alone. It affected no number here (247 warmup bars exceed every
  indicator period), but it would change live behaviour on restart and any backtest run with
  `--warmup-candles` below ~200. Recorded as a design lesson for any future additive sub-signal: gate it
  on at least one other sub-signal being present.
- **`TradingConfig::default()` has drifted from `experiments/baseline-config.json`** — unchanged from
  2026-09-21 and still unresolved. Code default is `allocation_threshold: 0.15, macd_fast: 52,
  macd_slow: 104, macd_signal: 18`; the pipeline's baseline file is `0.1 / 12 / 26 / 9`. No backtest is
  affected (every run passes `--config`), but a freshly-provisioned instance compiles in a different
  strategy from the one this loop measures. Still a judgement call about which is authoritative.
- **`--warmup-candles` still under-delivers** (247 of 300 requested). PR #29 fixes exactly this and is
  still open; not re-fixed here.
- **`shirube backtest-data push` still fails `403 Forbidden`** on the release-asset DELETE, restated
  rather than re-diagnosed: it is the Claude Code session-type policy applied above the token,
  established 2026-09-12, and must not be recorded as a lead again. The stored snapshot is now
  **thirteen days stale** (still the 2026-09-09 bootstrap at 33,452 bars). This run pulled it and
  backfilled a 15-day gap (17,290 bars from 196,500 executions in 393 requests, no history-limit hit)
  to reach **48,757 bars spanning 44 days**, and that work will be discarded when the container is
  reclaimed. The two documented ways out both still need a human decision.
- **The stored routine prompt remains out of date**, as every run since 2026-09-11 has noted. It still
  describes seeding `./run.db` from CoinGecko's hourly API and a single backtest per hypothesis; the doc
  replaced both. It also instructs that an algorithm variant touching `compute_btc_target`'s *body* be
  discarded entirely instead of PR'd, which contradicts both the doc and
  `experiments/hypotheses/README.md`. **Both of today's algorithm variants touched that body**, so for
  the second run running the conflict was live and stayed theoretical only because both were rejected.
  **Worth updating the routine's prompt.**

## Leads for the next run

1. **Build the bar-boundary volume history in `SignalEngine`.** Promoted to lead #1 because it is
   concrete, bounded, and gates an entire family. Without it, no volume-conditioned mechanism can ever
   affect live trading regardless of how it backtests — today's variant would have been a silent no-op
   in production. The agent identified the exact hazard (`MarketDataBus` republishing the in-progress
   candle via `peek_current()`) and the exact fix (append to the history only on a finalized bar
   transition, keyed on `open_time`). This is an enabling change, not a hypothesis, and should carry a
   regression test pinning that a partial candle never enters the buffer.
2. **Widen the holdout window.** Unchanged from 2026-09-20 and 2026-09-21, and strengthened again. The
   DB now spans **44 days**, so a 21- or 28-day holdout is available today. This run added a third
   independent instance of window instability (PR #27 swinging 3 → 94 trades and +8.15 → −1.10 Sharpe
   across two windows overlapping in 13 of 14 days, with no config change) and, worse, a case where a
   *mechanism* a previous run reasoned from did not reproduce a day later. A wider window averages over
   that. Doc change plus routine-prompt change, no code.
3. **Three mechanisms now flip sign between evaluation capitals**, not one: `signal_block_secs`
   (2026-09-21), `zone-damping-090` (PR #27), and now `relative-volume-damped-exposure`, which improves
   every primary-capital metric while producing this pipeline's worst-ever diagnostic-capital Sharpe

4. **Smooth the close-location signal rather than abandon it.** Today's rejection was a signal-to-noise
